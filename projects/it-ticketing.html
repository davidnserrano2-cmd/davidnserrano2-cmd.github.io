STARTING WITH CURIOSITY

What happens after someone clicks Submit?

I wanted to follow a request all the way through: collect it, validate it, store it, send a notification, and make the result visible. A ticketing system gave those experiments a clear structure.

BUILDING THE AUTOMATION

Three workflows to learn from.

Each workflow introduced another part of the problem: receiving data, handling an update, and using stored records to produce an output.

01

Employee submission

The form collects an email, category, title, description, and impact. The workflow checks references, sets priority, creates ticket and history records, attempts a Gmail confirmation, and returns the ticket number.

Practice: form triggers, field mapping, reference lookups, conditions, and database writes.

View the employee submission workflow

Configured form, database, Gmail, and confirmation steps in n8n.

02

Technician updates

A separate form supplies a ticket ID, technician email, new status, and notes. The workflow looks up the records, checks whether the status changed, records the update and history, and proceeds to notification and a form result.

Practice: linking records, conditional branches, change history, and different update outcomes.

View the technician update workflow

Lookups, change checks, ticket/history updates, and confirmation or conflict branches.

03

Daily operations report

A schedule trigger runs a PostgreSQL aggregate query and passes a report to Gmail. Captured output includes ticket totals, current status counts, high-priority tickets, and tickets created that day.

Practice: scheduled triggers, SQL aggregation, and turning stored data into a useful email output.

View the daily report workflow

Schedule trigger → PostgreSQL statistics query → Gmail report.

WHAT I LEARNED

Follow the data. Check each result.

The useful part of the project was working through the connections and seeing where assumptions needed a separate check.

Workflow steps have different outcomes

A stored ticket, an email attempt, and a successful form response are separate results. A confirmation page alone does not prove email delivery.

Visibility can be added carefully

A read-only dashboard made the records easier to inspect while existing workflows continued to own changes. Separating routes, queries, templates, and configuration also made the code easier to follow.

Models need evidence

The database accepts five status values, but that does not enforce transition order. Updating the diagrams helped distinguish the implemented system from earlier ideas.

VERIFICATION / COMPLETION SCOPE

A finished learning MVP.

The goal was to learn through a working local system and document it clearly. Further features can be separate projects.

What was checked

  • Reader connection, dashboard counts, search/filters, details, and audit history checked manually against PostgreSQL.
  • 21 automated dashboard tests using simulated records, covering validation, parameter binding, pagination, rendering, and error handling.
  • Final diagram field names, nullability, relationships, and allowed values checked against live database metadata.

Where the release stops

  • Local use without visitor authentication; database login and technician email lookup are not user authentication.
  • No public application hosting, dashboard editing, critical-alert workflow, or retry queue.
  • Workflow screenshots do not prove every failure path, transaction atomicity, or concurrency behavior.

Possible future work includes authenticated access, a standalone synthetic demo database, and deeper integration testing. Those ideas are outside this completed portfolio release.
